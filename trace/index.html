④两处取舍

取舍一：内联脚本 / 内联样式 vs 外链 SVG —— 缓存、可维护性、相对路径解析

缓存：内联脚本与样式随 HTML 同生共死——零额外请求、零缓存复用，HTML 一变全部失效重传；外链 SVG 可独立设置长缓存、跨页面复用，但也因此 README 里写死的绝对 URL 命中的是远端 main 分支的缓存快照，与本地文件脱钩。

可维护性：内联把 2.5KB 解码器钉死在页面里，改脚本必须改 HTML（本例还故意把载荷拆成 7 段 base64 藏进 DOM，进一步牺牲可读性换隐蔽）；外链 SVG 独立演进、独立审查，README 只持有一个引用。

相对路径解析：内联资源没有“路径”可言，天然免疫基准问题；外链资源则必须回答“相对谁解析”——README 的绝对 URL 以 raw.githubusercontent.com 的 main 目录为基准，本地同名文件以 README.md 所在目录为基准，两套基准各自解析，这正是第②段链不并线的原因。

取舍二：触发条件与分支过滤 → 反向约束产物目录与权限

触发面决定过滤需求：on 只有 schedule（每小时整点）与 workflow_dispatch，没有 push / pull_request，因此根本不需要 branches 过滤——分支约束退化为脚本里一行硬编码 const branch = "main"。

分支约束锁死产物目录：写入目标被钉在 main 分支的 .github/HISIHFPxsifNnF，产物目录只能是仓库内 .github/，而不是 Pages 站点或 Release——触发器不给路径，路径由脚本常量决定。

产物形态反推权限下限：“建一个提交”只需要 contents: write，于是 workflow 级与 job 级重复声明同一值即够；反过来，没有 pages: write、没有部署步骤，README 宣称的 GitHub Pages 发布目标在这条链上没有任何权限与步骤支撑——触发与过滤的收窄，最终暴露为发布目标的落空。
